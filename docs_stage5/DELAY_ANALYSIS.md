# 规划计时与真实物理延迟

## 计时协议

正式none主批使用多worker加速实验，物理时间在计算时暂停，其P95只能描述当时并发负载。本报告的公平计时另用单worker、OMP/MKL/OpenBLAS/NumExpr线程均为1，在其他登记实验和渲染进程退出后执行。

离线shadow在原A0真实执行的20/40/60秒锚点恢复完整REMUS状态、控制器积分/参考模型、执行器、历史命令和已经交付的观测。先做不计时的A0重放匹配，再以登记seed/规划周期决定轮转顺序，对A0–A5使用同一9候选集合。完整状态在每个预测后核对未改变。风险库加载不计入稳态规划耗时，所有方法每episode一次加载；不是测量每次重新加载模型的启动时间。

系统负载由标准Windows CPU计数器每2秒记录，机器CPU型号、线程环境、开始/结束时间与实际命令另存`exclusive_shadow_environment_20261012`。机器上正常OS及其他应用没有被关闭或宣称严格恒定；记录的系统CPU利用率包含本次任务。相同锚点配对与轮转顺序减少时序偏差，但少量锚点的P95不是硬实时最坏执行时间保证。

## 物理延迟定义

预登记的`multi_crossing3d g14 / seed523014 / noise0.02`分别运行A0–A5，其他参数与主比较相同。`measured`使用每次实际规划墙钟耗时，向上取整到0.02秒物理步，再加登记通信延迟。算法开始时只读取当时的实际车辆状态及已交付观测。

计算期间仍由原自动驾驶控制器执行前一个深度/航向/RPM参考，执行器滞后和六自由度车辆、障碍真值、感知交付/失联记忆继续按共同物理时间推进。新命令仅在ready时刻应用，不提前生效。串行worker没有重叠规划：下一决策至少等待规划周期，若计算超周期则等待该计算结束。RPM0应急同样只在命令就绪后执行且继续滑行。

这是显式计算延迟执行诊断，当前规划器没有为计算期间的状态位移重新预测或补偿。因此预测/实际误差包含继续旧指令造成的偏差，不能把它误标为确定性模型不一致。所有碰撞和1米判据仍基于完整真实积分轨迹及同步障碍采样间检查。

延迟组也采用单worker和相同线程设置；不与none的并发P95混合。每步日志保留planning_computation_delay_s、command_ready_time_s和command_application_time_s，供检查新命令是否提前或时间未推进。一个预登记复杂几何的六次任务只能检验本条件，不能认证所有静态/机动场景的实时能力。

## 原始控制与ready核对、日志语义修复

独立完整审查证据为`results_stage5/independent_raw_audit_20261012_v4.json`：六组累计48,501个实际控制区间，按实际规划墙钟重算0.02秒取整后的ready时刻，确认ready之前保持旧参考、之后才使用新参考，并核对下一次规划不与前次计算重叠。488次规划中483条参考实际应用，5条尾部待命令在任务结束时仍未到ready；不能算成已经执行。

物理忙窗口累计29,957个积分tick，六方法窗口位移中位数依次为1.5787/1.5648/1.5255/1.5257/1.5518/1.5512米，车辆与障碍时间持续推进。图中的A1/A5首次实际应用分别为1.16/1.24秒；此前控制日志仍是初始1100 RPM参考，而不是已计算的800 RPM参考。执行器实际转速仍按原滞后模型演化。

原始六任务使用的旧日志中，`selected_plans.command_application_time_s`直接保存**scheduled ready**。如A0最后130秒规划的该字段为131.16秒，任务130.44秒已结束，不能说131.16秒实际执行。已保存旧raw不改写，实际应用以`events.delayed_command_applied`为权威。新源代码增加独立`command_ready_time_s`，`command_application_time_s`初始为`None`，只有实际应用才填物理时刻；这个兼容日志修复没有改变车辆、命令或时间推进数值。

本例共同观测周期2秒、规划起点按2秒对齐，而实际最长计算延迟1.5–1.7秒，所以忙窗口内部新增感知采样数为0。代码继续推进感知/记忆，但这六次**没有实测覆盖“计算中有新观测到达”的压力条件**，不能据此宣布所有感知延迟/高采样率均被验证。
